# AI Drama Studio V3 阶段人工验收规范

> 日期：2026-09-09  
> 目的：保证每一个开发阶段不仅“代码完成、自动测试通过”，还必须让项目使用者能够亲自在产品里验收该阶段的真实行为。  
> 架构原则：工程阶段可以逐项验收，但普通用户产品流程必须按业务结果组织；视频 P5/P6/P7/P8 统一归属于“原片理解”业务阶段。

---

# 1. 阶段完成必须同时满足三层

以后每个 P 阶段统一区分：

```text
1. 代码完成
2. 自动测试完成
3. 人工可验收
```

任何阶段如果只有前两项，没有用户可以操作的验收入口或清晰的人工验收方法，不应视为完整收口。

真实模型相关阶段另外增加：

```text
4. 真实模型 / 真实素材验收
```

不能把 mock、单元测试或“代码已接入”写成真实模型验收通过。

还必须额外区分：

```text
工程验收入口
!=
最终普通用户主流程
```

例如 P5 可以保留独立 Shot Boundary Command 用于人工技术验收，但普通用户不应该被要求“先完成 P5，再点击 P6，再点击 P7”。

---

# 2. 人工验收入口原则

人工验收必须满足：

- 用户可以从前端页面或明确的开发 / 技术验收入口主动启动；
- GET / 页面刷新仍然只读，不能因为打开页面偷偷执行任务；
- 测试动作必须由显式 POST / Command 触发；
- 页面要展示普通用户能理解的业务结果，不要求用户阅读数据库、日志、fingerprint 或 ProviderJob 内部字段；
- 内部技术能力可以放在“技术分析详情 / 开发验收”区域；
- 基础设施阶段允许使用本地 mock，但必须明确“不会调用真实模型、不产生费用”；
- mock 只能验证当前阶段的机制，禁止借验收工具提前开发后续阶段；
- 后续真实业务阶段优先直接使用真实输入素材进行人工验收；
- 某个内部 Task 成功不能自动等同整个 Product Stage 完成。

---

# 3. P4 人工验收

P4 的业务能力是 Task / ProviderJob / Guardrail，本阶段人工验收使用本地模拟任务，不调用真实模型。

项目工作区：

```text
开发验收工具
→ P4 任务执行机制
```

提供正常完成、失败重试、中断继续、防重复提交四个测试入口。

正常完成必须验证：

```text
排队中
→ 处理中
→ 进度持续变化
→ 已完成 100%
```

失败 / 重试必须验证 attempt 增加；中断 / 继续必须保留 checkpoint；防重复提交必须验证同一 Idempotency-Key 只产生一个 Task。

Provider mock 也必须验证 ProviderJob 在模拟 remote call 前已经 commit。

普通任务卡只展示业务可理解的状态、进度、失败原因、重试、继续、取消，不展示 API Key、ProviderJob payload、worker id 等内部字段。

# 4. P5 镜头技术锚点人工验收

P5 必须使用用户自己的真实 Episode 做页面验收，只验收：

```text
完整 Episode
→ Shot Boundary
→ thumbnail
→ Reference Clip
→ Task 状态
→ CURRENT / STALE
```

不验收 ASR / OCR / 剧情理解 / P7 / P8。

## 4.1 输入与只读加载

视频项目为空时应显示“还没有原片 → 上传原片”。上传后 Episode 自动出现；刷新页面只读当前状态，不得自动创建 Shot Boundary Task。

完整 Episode 必须一直保留为 Source Truth，Reference Clip 只是派生预览 / 局部精看资产。

## 4.2 显式运行与结果检查

在技术分析详情中显式点击“生成技术锚点”。成功后人工检查：

- Shot 编号连续递增；
- start < end；
- Shot 时间有序且边界连续；
- 首镜 / 尾镜覆盖 Episode；
- thumbnail 与镜头相符；
- Reference Clip 可以播放、完整解码、内容对应；
- 明显硬切 / 淡入淡出 / 白闪等常见短剧转场质量合理；
- 快速动作不应造成大面积误切。

Source Video 变化后旧 SHOT_ANCHORS 必须 STALE。

项目使用者已经用一条约 1:06 的真实竖屏短剧跑通 28 个 CURRENT Shot Anchors、thumbnail 与 Reference Clip，因此 P5 已完成真实素材验收。

# 5. P6 Source Evidence 人工验收要求

P6 工程代码与用户真实短剧人工验收均已完成，`SOURCE_DIALOGUE_EVIDENCE` capability 已为 `AVAILABLE`。以下要求继续保留为回归验收规范。

## 5.1 显式运行真实 ASR + OCR

项目工作区 P6 开发验收面板必须通过显式 Episode Command 启动：

```text
POST /projects/{project_id}/episodes/{episode_id}/commands/source-evidence
```

真实执行路径必须是：

```text
完整 Episode 连续音轨
→ ASR

完整 Episode 视频时间轴
→ OCR
```

严禁：

```text
每个 Reference Clip 分开 ASR
→ 再拼回完整对白
```

Shot Anchors 可以不存在；存在时只能辅助 OCR 抽帧 / 去冗余和对白 Shot 时间投影。

## 5.2 Canonical 对白 / OCR

人工检查：

- 对白原文与真实语音基本一致；
- 时间戳合理；
- 跨 Shot 的一句对白仍是一条 canonical utterance；
- Shot projection 可以是 1:N，但不复制 / 改写正文；
- OCR 文本与真实画面文字对应；
- OCR 连续重复合理合并；
- OCR 时间范围合理。

多 Episode 项目只有全集均存在 CURRENT Evidence 后，才允许发布项目级 `SOURCE_DIALOGUE`。

Source Video 变化后旧 Episode Evidence / 项目级 SOURCE_DIALOGUE 必须 STALE。

2026-09-09 项目使用者已明确确认真实短剧 P6 人工验收通过：

```text
P6 = ✅ 完成
SOURCE_DIALOGUE_EVIDENCE = AVAILABLE
```

# 6. P7 整集多模态理解人工验收要求

P7 当前处于**工程实现与 CI 收口阶段**。即使代码和自动测试全部通过，在下面的真实模型 / 真实短剧验收完成以前，也不得写成 P7 完成。

P7 只对：

```text
REPLICA
REDRAW
```

开放；`TRANSLATION` 不执行 SOURCE_BIBLE。

## 6.1 固定输入契约

每次真实验收必须同时确认：

```text
完整 immutable Episode
+
CURRENT Source Evidence
+
可选 CURRENT Shot Anchors
```

其中：

- 完整 Episode 是 Source Truth；
- Provider 必须直接接收完整 Episode，而不是 20/30 个 Reference Clip；
- P6 canonical dialogue / OCR 是文字事实源；
- Shot Anchors 只是定位提示，缺失不能阻塞 P7；
- semantic window 可以重叠，不得伪装成 Shot Boundary；
- 模型不能根据视频音轨重新转写并覆盖 P6 canonical dialogue。

## 6.2 三个正式模型选项

项目工作区 P7 设置必须只对普通用户展示三个正式模型档位：

```text
1. Doubao Seed 2.1 Pro
   火山引擎 Ark API
   云端生产档

2. Qwen3.8-27B
   本地 / 局域网 vLLM OpenAI-compatible
   本地高质量档

3. Qwen3-VL-8B-Thinking
   本地 / 局域网 vLLM OpenAI-compatible
   低显存兼容档
```

API Key、本地服务地址、磁盘路径、tensor parallel、量化参数不应该由普通用户在项目页面输入或存入 Project。

模型选择是 Project 级业务配置，必须进入 P7 fingerprint / provenance。

## 6.3 模型切换 STALE 验收

先用任意一个模型得到 CURRENT SOURCE_BIBLE，然后切换到另一个模型并保存。

预期：

```text
旧 SOURCE_BIBLE       → STALE
旧 STORY_SKELETON     → STALE
旧 RHYTHM_SKELETON    → STALE
P6 Source Evidence    → 仍 CURRENT
```

页面不得出现“当前选择 Qwen3.8，但 Doubao 生成的 SOURCE_BIBLE 仍显示 CURRENT”的假状态。

切换设置本身不得偷偷运行模型；用户必须再次显式执行 P7 Command。

## 6.4 Doubao Seed 2.1 Pro 真实 API 验收

后端本地 `.env` 配置真实 Ark API Key，项目页面选择：

```text
Doubao Seed 2.1 Pro
```

用用户自己的真实短剧运行整集理解。

必须验证：

- Ark Files API 上传的是完整 Episode；
- ProviderJob 在外部请求前已经 commit；
- 远端文件可处理并进入 Responses 调用；
- `input_video` 与 P7 Evidence prompt 同时进入模型；
- 返回结果通过 Pydantic / Evidence ID / time range 校验；
- 失败时不能发布半成品 SOURCE_BIBLE；
- 成功时 Provider / model / ProviderJob provenance 正确；
- 远端临时文件执行 best-effort cleanup；
- 真实延迟和费用可接受。

自动测试只能证明 adapter / guardrail，不等于本项通过。

## 6.5 Qwen3.8-27B 本地真实验收

启动真实 vLLM OpenAI-compatible 服务，并确保：

- backend 与 vLLM 能访问同一个完整 Episode 文件路径；
- vLLM 允许 local media path；
- 项目设置选择 `Qwen3.8-27B`；
- P7 调用通过 `video_url=file://...` 读取完整 Episode。

人工确认：

- 模型能处理真实 Episode 而不是只接图片；
- SOURCE_BIBLE JSON 可稳定通过服务端 schema 校验；
- 人物、人物关系、剧情因果和时间化剧情质量可用；
- 不产生脱离 P6 Evidence 的假对白；
- provider/model provenance 显示为当前本地模型；
- 本机实际显存、速度、量化方案达到可接受水平。

该模型是当前本地高质量主候选。

## 6.6 Qwen3-VL-8B-Thinking 本地兼容验收

以相同真实 Episode / 相同 P6 Evidence 运行 8B Thinking。

验收重点除了 6.5 相同的数据正确性外，还要比较：

- 显存占用是否显著更低；
- 推理速度是否更适合轻量机器；
- 人物混淆、剧情因果、关系变化、Story Beats 是否明显掉档；
- Thinking 输出中若 runtime 暴露 `<think>`，不得把 reasoning 文本写入 SOURCE_BIBLE；最终只能持久化合法 JSON 业务结果。

8B 的定位是低显存兼容档，不要求质量超过 Qwen3.8-27B，但必须达到“可用”最低线。

## 6.7 同源 A/B 验收

为了避免“不同素材导致主观错觉”，模型质量比较必须至少使用同一组：

```text
同一完整 Episode
+
同一 CURRENT P6 Source Evidence
+
同一可选 Shot Anchors
+
同一 SOURCE_BIBLE schema / prompt version
```

优先比较：

```text
Doubao Seed 2.1 Pro
vs
Qwen3.8-27B
```

8B 作为资源兼容对照。

人工至少逐项检查：

1. 整集故事概述是否真的看懂；
2. 人物是否混淆；
3. 人物关系及其变化是否正确；
4. 场景与关键道具是否正确；
5. 时间化剧情是否对得上原片；
6. Hook / 冲突 / 升级 / 反转 / 情绪峰值是否准确；
7. Story Skeleton 是否覆盖关键因果；
8. Rhythm Skeleton 是否与真实剪辑 / 对白反应节奏一致；
9. Evidence ID 是否只引用 CURRENT P6 记录；
10. 是否出现模型自编对白 / OCR / 身份事实。

## 6.8 SOURCE_BIBLE 用户结果验收

成功后项目工作区必须能直接阅读《源作概览分析》，而不是只显示“Task succeeded”。

至少可见：

```text
素材基线
整体分析
时间化原作剧情
人物 / 人物关系
场景
关键道具
Story / 关键事件
情绪时间线
Story Skeleton
Rhythm Skeleton
revision / provenance
```

用户应能从 timed story 的 Evidence ID 反查 P6 canonical 对白 / OCR 正文。

## 6.9 编辑 / revision 验收

在 CURRENT SOURCE_BIBLE 上修改例如故事概述并保存。

预期：

```text
SOURCE_BIBLE rev1 → STALE
SOURCE_BIBLE rev2 → CURRENT
旧 Story / Rhythm → STALE
新 Story / Rhythm → CURRENT
P6 dialogue / OCR → 原文完全不变
```

媒体基线（Episode ID、原始文件名、时长、分辨率、fps、codec 等）不能被用户编辑覆盖。

## 6.10 fail-closed 验收

真实模型或开发测试至少验证这些错误不能发布 SOURCE_BIBLE：

- 引用不存在的 dialogue / OCR Evidence ID；
- 时间窗口超过 Episode duration；
- 人物关系引用不存在的 character ID；
- Provider 返回非合法 JSON / schema 不匹配；
- P7 Task 创建后上游 Source / Evidence / 模型选择发生变化。

## 6.11 P7 完成标准

只有以下全部满足，才允许用户确认 P7 完成：

- 当前 `main` CI 全绿；
- 三模型选择 UI / Project 持久化 / STALE 行为通过；
- Doubao Seed 2.1 Pro 真实 Ark API 用用户真实短剧至少跑通一条；
- 至少一个本地模型（优先 Qwen3.8-27B）以真实 vLLM + 真实完整 Episode 跑通；
- 对同源 Episode 做人工剧情 / 人物 / 时间线 / Evidence 质量核对；
- SOURCE_BIBLE 可读、可编辑、可生成新 revision；
- P6 canonical Evidence 在 P7 生成、切换模型、人工编辑后仍保持不变；
- provenance 能追到准确的上游 Artifact / EvidenceSet / ProviderJob / model；
- 用户明确确认真实短剧质量通过。

在完成以上验收以前：

```text
P7 = 🟡 未收口
EPISODE_UNDERSTANDING != AVAILABLE
STORY_RHYTHM != AVAILABLE
P8 = 不开始
```

# 7. P8 逐镜精细拉片人工验收要求

P8 必须在 P7 整集知识已经建立并人工验收后执行。

禁止路径：

```text
每个 Shot 单独丢给模型猜剧情
→ 最后拼成整集
```

正确路径：

```text
Source Bible / Story / Rhythm
+
Shot Anchors / Reference Clip
↓
逐镜精细拉片
```

人工重点检查镜头中的人物、动作、表情、场景、道具、景别、构图、运镜、连续性和剧情功能是否利用了整集上下文，而不是局部盲猜。

当前 P8 尚未开始。

# 8. 后续统一要求

后续所有阶段继续按本规范执行：

- 工程能力可以逐切片验收；
- 普通产品界面按业务阶段组织；
- GET 无副作用；
- 真实 Provider 必须真实验收；
- 自动测试不能冒充用户真实素材质量；
- 内部 Artifact / Evidence 必须可追溯；
- 不把技术成功冒充业务完成。
