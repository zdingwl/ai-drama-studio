# AI Drama Studio V3 阶段人工验收规范

> 日期：2026-09-08  
> 目的：保证每一个开发阶段不仅“代码完成、自动测试通过”，还必须让项目使用者能够亲自在产品里验收该阶段的真实行为。

---

# 1. 阶段完成必须同时满足三层

以后每个 P 阶段统一区分：

```text
1. 代码完成
2. 自动测试完成
3. 人工可验收
```

任何阶段如果只有前两项，没有用户可以操作的验收入口或清晰的人工验收方法，不应视为完整收口。

真实模型相关阶段另外增加：

```text
4. 真实模型 / 真实素材验收
```

不能把 mock、单元测试或“代码已接入”写成真实模型验收通过。

---

# 2. 人工验收入口原则

人工验收必须满足：

- 用户可以从前端页面或明确的开发验收入口主动启动；
- GET / 页面刷新仍然只读，不能因为打开页面偷偷执行任务；
- 测试动作必须由显式 POST / Command 触发；
- 页面要展示普通用户能理解的结果，不要求用户阅读数据库、日志、fingerprint 或 ProviderJob 内部字段；
- 基础设施阶段允许使用本地 mock，但必须明确“不会调用真实模型、不产生费用”；
- mock 只能验证当前阶段的机制，禁止借验收工具提前开发后续阶段；
- 后续真实业务阶段优先直接使用真实输入素材进行人工验收。

# 3. P4 人工验收

P4 的业务能力是 Task / ProviderJob / Guardrail，本阶段没有 Shot Boundary、ASR、OCR、Step 3.7 Flash 或 MiniMax H3，因此人工验收使用本地模拟任务，不调用真实模型。

项目工作区：

```text
开发验收工具
→ P4 任务执行机制
```

提供四个测试入口。

## 3.1 测试正常完成

点击：

```text
测试正常完成
```

预期：

```text
排队中
→ 处理中
→ 进度持续变化
→ 已完成 100%
```

运行过程中应该出现“取消”按钮，可以人工测试 cooperative cancel。

正常验收任务内部运行本地 Provider mock，并验证 ProviderJob 在模拟 remote call 前已经 commit。不会产生真实模型费用。

## 3.2 测试失败 → 重试

第一次预期：

```text
进度到 40%
→ 失败
→ 显示失败原因
→ 出现“重试”按钮
```

点击重试后：

```text
重新排队
→ 再次执行
→ attempt 增加
→ 最终完成 100%
```

## 3.3 测试中断 → 继续

第一次预期：

```text
进度到 55%
→ 保存 checkpoint
→ 已中断
→ 出现“继续”按钮
```

点击继续后：

```text
保留原检查点
→ 重新排队
→ 从已有进度继续
→ 最终完成 100%
```

## 3.4 测试防重复提交

点击：

```text
测试防重复提交
```

前端用同一个 Idempotency-Key 并发发出两次完全相同的 Command。只有同时满足：

```text
两次 POST 返回同一个 Task ID
+
本次测试前后任务总数只增加 1
```

才允许显示通过。

---

# 4. P4 页面验收边界

普通任务卡只展示：

```text
任务名称
状态
进度
失败原因
重试
继续
取消
```

不展示：

```text
ProviderJob
payload fingerprint
checkpoint JSON
API Key
Authorization
worker id
内部 provider / model 技术字段
```

P4 验收工具和 Task 区域独立于 ProjectExecutionPlan；即使当前 Plan 尚未生成，也可以单独人工验收 P4。

# 5. P5 视频技术预处理人工验收

P5 必须使用用户自己的真实 Episode 做页面验收。

本阶段只验收：

```text
原片上传 / Episode
→ Shot Boundary
→ thumbnail
→ Reference Clip
→ Task 状态
→ CURRENT / STALE
```

不验收、也不应该出现：

```text
ASR
OCR
对白理解
人物识别
剧情理解
Step 3.7 Flash
逐镜语义拉片
```

## 5.1 空项目上传入口

进入一个视频项目：

```text
REPLICA
REDRAW
TRANSLATION
```

如果当前项目没有任何 Episode，预期工作区“视频技术预处理 / 镜头边界”区域直接显示：

```text
还没有原片
上传原片
```

不得出现“读取已上传剧集”这种要求用户手动读取空列表的按钮。

点击“上传原片”，选择一集或多集自己真实的短剧视频。

预期：

- 上传成功后 Episode 列表自动出现；
- 不需要额外点击“读取”；
- 上传只是 P3 Source 输入 POST，不会自动启动 Shot Boundary；
- Source 更新后旧执行计划会失效，需要按当前 Source 状态重新生成 Plan。

## 5.2 已有 Episode 的只读加载

如果项目已经上传过 Episode，重新进入页面或刷新页面。

预期：

- Episode 自动显示；
- 第一集可以自动作为当前选择；
- 页面可以只读 GET 当前 Shot Boundary 状态；
- 页面刷新不能创建新 Task；
- 页面刷新不能自动开始视频处理；
- 只有用户显式点击“开始处理这一集”才允许创建 P5 Task。

## 5.3 显式启动 Shot Boundary

选择一集真实短剧后，点击：

```text
开始处理这一集
```

预期任务区出现：

```text
第 N 集：镜头技术预处理
```

状态应能看到：

```text
排队中
→ 处理中
→ 进度变化
→ 已完成
```

如果视频较长，可以在处理中点击“取消”，验证 cooperative cancel。

如果任务真实失败，应显示普通用户可理解的安全失败原因，并在可重试时出现“重试”。重试仍必须走显式 POST Command。

## 5.4 Shot 结果验收

任务成功后回到镜头区域。

预期状态：

```text
当前有效
```

并直接显示 Shot 数量和每个 Shot：

```text
镜头编号
开始时间
结束时间
时长
缩略图
Reference Clip 播放器
```

人工检查至少包括：

- Shot 编号从 1 连续递增；
- `start < end`；
- Shot 按时间升序；
- Shot 之间不重叠；
- 第一镜从 Episode 起点开始；
- 最后一镜覆盖到 Episode 结束；
- 相邻 Shot 的时间边界连续；
- thumbnail 与该 Shot 内容相符；
- Reference Clip 可以直接播放；
- Reference Clip 内容和该 Shot 时间范围一致；
- Reference Clip 不是空文件、黑屏占位或无法完整解码的假结果。

## 5.5 短剧常见转场重点检查

推荐拿一集同时包含以下情况的真实短剧验收：

```text
硬切
淡入
淡出
闪白 / 白场转场
快速人物动作
快速镜头运动
```

重点判断：

- 明显硬切应形成边界；
- 淡黑 / 淡入淡出应尽量形成合理边界；
- 闪白附近不应完全漏检；
- 快速动作本身不应造成大面积连续误切；
- 极短视觉变化不应无限碎片化成大量无意义 Shot。

P5 使用多 detector + 后过滤设计，但真实短剧质量仍必须由人工看实际素材判断，自动测试不能替代这一项。

## 5.6 Source Video 变化后的 STALE

在已经成功得到 Shot Boundary 后，改变 Source Video，例如：

```text
继续上传 Episode
或
调整 Episode 顺序
```

预期：

- 新 `SOURCE_VIDEO` revision 成为 CURRENT；
- 依赖旧 Source 的 `SHOT_ANCHORS` 自动 STALE；
- 页面旧结果显示“原片已变化，需要重新处理”；
- 旧 Shot Boundary 不能继续作为 CURRENT 下游输入；
- 用户重新处理后形成新的正式结果。

## 5.7 普通用户页面技术细节边界

P5 页面可以展示业务结果，但不得展示：

```text
FFmpeg 命令参数
PySceneDetect detector 参数
adaptive threshold
fingerprint
ProviderJob
checkpoint JSON
磁盘内部路径
source SHA256
```

用户应该只看到素材、任务状态和 Shot 结果。

## 5.8 P5 人工验收完成定义

只有项目使用者实际拿自己的短剧完成至少一集上述检查，才能写：

```text
P5 用户真实素材人工验收：通过
```

当前 CI 动态生成真实可解码媒体，只证明技术管线工作，不等于用户真实短剧质量已经人工验收通过。

---

# 6. 后续阶段要求

P6 必须能够让用户用真实音视频检查 ASR / OCR / Source Dialogue 结果。

P7 进入真实整集理解模型后，必须增加真实 Episode 的模型验收，不能只靠 mock 或结构化输出单测。

后续所有阶段继续按本规范执行。
