# AI Drama Studio V3 阶段人工验收规范

> 日期：2026-09-09  
> 目的：保证每一个开发阶段不仅“代码完成、自动测试通过”，还必须让项目使用者能够亲自在产品里验收该阶段的真实行为。  
> 架构原则：工程阶段可以逐项验收，但普通用户产品流程必须按业务结果组织；视频 P5/P6/P7/P8 统一归属于“原片理解”业务阶段。

---

# 1. 阶段完成必须同时满足三层

以后每个 P 阶段统一区分：

```text
1. 代码完成
2. 自动测试完成
3. 人工可验收
```

任何阶段如果只有前两项，没有用户可以操作的验收入口或清晰的人工验收方法，不应视为完整收口。

真实模型相关阶段另外增加：

```text
4. 真实模型 / 真实素材验收
```

不能把 mock、单元测试或“代码已接入”写成真实模型验收通过。

还必须额外区分：

```text
工程验收入口
!=
最终普通用户主流程
```

例如 P5 可以保留独立 Shot Boundary Command 用于人工技术验收，但普通用户不应该被要求“先完成 P5，再点击 P6，再点击 P7”。

---

# 2. 人工验收入口原则

人工验收必须满足：

- 用户可以从前端页面或明确的开发 / 技术验收入口主动启动；
- GET / 页面刷新仍然只读，不能因为打开页面偷偷执行任务；
- 测试动作必须由显式 POST / Command 触发；
- 页面要展示普通用户能理解的业务结果，不要求用户阅读数据库、日志、fingerprint 或 ProviderJob 内部字段；
- 内部技术能力可以放在“技术分析详情 / 开发验收”区域；
- 基础设施阶段允许使用本地 mock，但必须明确“不会调用真实模型、不产生费用”；
- mock 只能验证当前阶段的机制，禁止借验收工具提前开发后续阶段；
- 后续真实业务阶段优先直接使用真实输入素材进行人工验收；
- 某个内部 Task 成功不能自动等同整个 Product Stage 完成。

---

# 3. P4 人工验收

P4 的业务能力是 Task / ProviderJob / Guardrail，本阶段没有 Shot Boundary、ASR、OCR、Step 3.7 Flash 或 MiniMax H3，因此人工验收使用本地模拟任务，不调用真实模型。

项目工作区：

```text
开发验收工具
→ P4 任务执行机制
```

提供四个测试入口。

## 3.1 测试正常完成

点击：

```text
测试正常完成
```

预期：

```text
排队中
→ 处理中
→ 进度持续变化
→ 已完成 100%
```

运行过程中应该出现“取消”按钮，可以人工测试 cooperative cancel。

正常验收任务内部运行本地 Provider mock，并验证 ProviderJob 在模拟 remote call 前已经 commit。不会产生真实模型费用。

## 3.2 测试失败 → 重试

第一次预期：

```text
进度到 40%
→ 失败
→ 显示失败原因
→ 出现“重试”按钮
```

点击重试后：

```text
重新排队
→ 再次执行
→ attempt 增加
→ 最终完成 100%
```

## 3.3 测试中断 → 继续

第一次预期：

```text
进度到 55%
→ 保存 checkpoint
→ 已中断
→ 出现“继续”按钮
```

点击继续后：

```text
保留原检查点
→ 重新排队
→ 从已有进度继续
→ 最终完成 100%
```

## 3.4 测试防重复提交

点击：

```text
测试防重复提交
```

前端用同一个 Idempotency-Key 并发发出两次完全相同的 Command。只有同时满足：

```text
两次 POST 返回同一个 Task ID
+
本次测试前后任务总数只增加 1
```

才允许显示通过。

# 4. P4 页面验收边界

普通任务卡只展示：

```text
任务名称
状态
进度
失败原因
重试
继续
取消
```

不展示：

```text
ProviderJob
payload fingerprint
checkpoint JSON
API Key
Authorization
worker id
内部 provider / model 技术字段
```

P4 验收工具和 Task 区域独立于 ProjectExecutionPlan；即使当前 Plan 尚未生成，也可以单独人工验收 P4。

# 5. P5 镜头技术锚点人工验收

P5 必须使用用户自己的真实 Episode 做页面验收。

P5 是“原片理解”业务阶段内部的一项技术能力。本阶段只验收：

```text
完整 Episode
→ Shot Boundary
→ thumbnail
→ Reference Clip
→ Task 状态
→ CURRENT / STALE
```

不验收、也不应该被写成已经完成：

```text
ASR
OCR
对白理解
人物识别
剧情理解
Step 3.7 Flash
逐镜语义拉片
原片理解业务阶段整体完成
```

## 5.1 空项目上传入口

进入一个视频项目：

```text
REPLICA
REDRAW
TRANSLATION
```

如果当前项目没有任何 Episode，预期主工作区显示：

```text
原片理解
→ 还没有原片
→ 上传原片
```

不得出现“读取已上传剧集”这种要求用户手动读取空列表的按钮。

点击“上传原片”，选择一集或多集自己真实的短剧视频。

预期：

- 上传成功后 Episode 列表自动出现；
- 不需要额外点击“读取”；
- 上传只是 P3 Source 输入 POST，不会自动启动 Shot Boundary；
- 页面明确完整 Episode 是 Source Truth；
- Source 更新后旧执行计划会失效，需要按当前 Source 状态重新生成 Plan。

## 5.2 已有 Episode 的只读加载

如果项目已经上传过 Episode，重新进入页面或刷新页面。

预期：

- Episode 自动显示；
- 第一集可以自动作为当前选择；
- 页面可以只读 GET 当前 Shot Anchors 状态；
- 页面刷新不能创建新 Task；
- 页面刷新不能自动开始视频处理；
- 主页面标题是“原片理解”，不是“视频技术预处理”。

## 5.3 产品层与技术详情分层

主页面应能看到类似：

```text
完整原片                已就绪
镜头技术锚点            当前有效 / 未生成
对白与画面文字证据      能力待接入
整集多模态理解          能力待接入
逐镜精细拉片            能力待接入
```

P5 Shot 详情必须位于默认收起的：

```text
技术分析详情
```

展开后才看到：

```text
镜头技术锚点
Shot / thumbnail / Reference Clip
```

验收重点：

- 28 个 Shot 等技术结果不再占据普通用户主工作区；
- Shot Boundary 成功不能让页面把“原片理解”标记成完成；
- Raw Internal PlanStep 默认不作为 Product Plan 逐项展示；
- Product Plan 应按业务阶段聚合；
- 开发 / 排障时仍可查看内部步骤。

## 5.4 显式启动 Shot Boundary 技术任务

展开“技术分析详情”，选择真实 Episode，点击：

```text
生成技术锚点
```

已有 CURRENT 结果时可以显示：

```text
重新生成技术锚点
```

预期任务区出现对应 Shot Boundary 技术 Task。

状态应能看到：

```text
排队中
→ 处理中
→ 进度变化
→ 已完成
```

如果视频较长，可以在处理中点击“取消”，验证 cooperative cancel。

如果任务真实失败，应显示普通用户可理解的安全失败原因，并在可重试时出现“重试”。重试仍必须走显式 POST Command。

该独立按钮属于当前 P5 技术验收 / 高级详情入口；未来产品主路径由更高层“开始原片理解” Command 统一编排内部能力。

## 5.5 Shot 结果验收

任务成功后展开技术详情。

预期状态：

```text
技术锚点当前有效
```

并显示 Shot 数量和每个 Shot：

```text
镜头编号
开始时间
结束时间
时长
缩略图
Reference Clip（按需播放）
```

人工检查至少包括：

- Shot 编号从 1 连续递增；
- `start < end`；
- Shot 按时间升序；
- Shot 之间不重叠；
- 第一镜从 Episode 起点开始；
- 最后一镜覆盖到 Episode 结束；
- 相邻 Shot 的时间边界连续；
- thumbnail 与该 Shot 内容相符；
- Reference Clip 可以直接播放；
- Reference Clip 内容和该 Shot 时间范围一致；
- Reference Clip 不是空文件、黑屏占位或无法完整解码的假结果；
- 默认不一次创建所有 Shot 的 `<video>` 播放器，用户选中某一 Shot 后才播放该片段。

## 5.6 短剧常见转场重点检查

推荐拿一集同时包含以下情况的真实短剧验收：

```text
硬切
淡入
淡出
闪白 / 白场转场
快速人物动作
快速镜头运动
```

重点判断：

- 明显硬切应形成边界；
- 淡黑 / 淡入淡出应尽量形成合理边界；
- 闪白附近不应完全漏检；
- 快速动作本身不应造成大面积连续误切；
- 极短视觉变化不应无限碎片化成大量无意义 Shot。

P5 使用多 detector + 后过滤设计，但真实短剧质量仍必须由人工看实际素材判断，自动测试不能替代这一项。

## 5.7 Source Video 变化后的 STALE

在已经成功得到 Shot Anchors 后，改变 Source Video，例如：

```text
继续上传 Episode
或
调整 Episode 顺序
```

预期：

- 新 `SOURCE_VIDEO` revision 成为 CURRENT；
- 依赖旧 Source 的 `SHOT_ANCHORS` 自动 STALE；
- 页面旧结果显示“原片已变化，需要更新锚点”；
- 旧 Shot Boundary 不能继续作为 CURRENT 下游输入；
- 用户 / orchestration 重新处理后形成新的正式结果。

## 5.8 完整 Episode Source Truth 验收

P5 生成任何 Reference Clip 后，都要确认：

- 原始 Episode 仍保留；
- 后续 Source Evidence 与整集理解的契约仍指向完整 `SOURCE_VIDEO`；
- Reference Clip 只是派生预览 / 局部精看资产；
- 不存在“删除完整 Episode，只剩 28 个小视频”的流程；
- 不存在“P6 对 28 个小视频分别做 ASR 再拼回对白”的契约。

## 5.9 普通用户页面技术细节边界

技术详情可以展示业务可理解的 Shot 结果，但不得展示：

```text
FFmpeg 命令参数
PySceneDetect detector 参数
adaptive threshold
fingerprint
ProviderJob
checkpoint JSON
磁盘内部路径
source SHA256
```

## 5.10 P5 当前真实素材状态

项目使用者已经拿一条约 1:06 的真实竖屏短剧跑通：

```text
CURRENT Shot Anchors
28 个 Shot
thumbnail 可见
Reference Clip 可播放
Task succeeded
```

因此 P5 的真实素材技术链已经获得一条实际通过样本。

仍需持续积累更多含复杂淡入淡出 / 白闪 / 快速运动的素材质量样本。该结果不能被写成 P6/P7/P8 或“原片理解完成”。

# 6. P6 Source Evidence 人工验收要求

P6 工程代码与用户真实短剧人工验收均已完成，`SOURCE_DIALOGUE_EVIDENCE` capability 已切换为 `AVAILABLE`。以下要求继续保留为 P6 回归验收规范。

P6 不新增普通用户独立页面。项目工作区底部提供工程验收入口：

```text
P6 开发验收 · Source Evidence
```

该面板属于开发 / 技术验收区域，不改变普通用户“原片理解”主流程。

## 6.1 页面只读加载

进入已有真实 Episode 的视频项目并打开项目工作区。

预期：

- 页面底部出现 `P6 开发验收 · Source Evidence`；
- 可以选择当前 Episode；
- 面板会只读 GET 当前 Evidence 状态；
- 页面打开 / 刷新不会自动启动 ASR 或 OCR；
- 未运行时显示 `NOT_BUILT`；
- 已有当前结果时显示 `CURRENT`；
- Source 变化后的旧结果显示 `STALE`。

## 6.2 显式运行真实 ASR + OCR

选择一集用户自己的真实短剧，点击：

```text
运行真实 ASR + OCR
```

已有 CURRENT 结果时允许显示：

```text
重新运行真实 ASR + OCR
```

该按钮必须走 Episode 级显式 Command：

```text
POST /projects/{project_id}/episodes/{episode_id}/commands/source-evidence
```

预期任务状态：

```text
排队中
→ 处理中
→ 进度变化
→ 已完成
```

工程验收必须确认真实执行路径是：

```text
完整 Episode 音轨
→ 连续 ASR

完整 Episode 视频时间轴
→ OCR
```

而不是：

```text
Shot 001.mp4 → ASR
Shot 002.mp4 → ASR
...
→ 拼句子
```

Shot Anchors 可以不存在；P6 仍应能启动和完成。存在 CURRENT Shot Anchors 时，只允许用于 OCR 抽帧提示和 canonical dialogue 的 Shot 时间投影。

## 6.3 Canonical 对白人工检查

任务成功后，面板应展示：

```text
Canonical 对白
开始时间 → 结束时间
对白正文
语言
Projected Shot numbers
```

至少人工核对：

- 对白原文与真实短剧语音基本一致；
- 对白开始 / 结束时间与真实说话时间合理贴合；
- ASR 分段不能因为 Shot Boundary 被强制截断；
- 一句对白跨 Shot 时仍只有一条 canonical utterance；
- 该 utterance 可以投影到多个 Shot，例如 `Shot 12, 13`；
- `ShotDialogueProjection` 只表达时间重叠关系，不复制或改写 canonical 对白正文。

如果真实短剧里没有恰好跨 Shot 的一句对白，应换一个明确存在该情况的真实片段继续验收，不能用 synthetic pytest 代替这一项。

## 6.4 OCR 人工检查

面板应展示：

```text
画面文字 OCR
开始时间 → 结束时间
canonical OCR 文本
confidence
```

至少人工核对：

- 片头字卡、剧情字幕、屏幕文字等真实可见文本是否被提取；
- OCR 时间范围与文字实际出现位置大致一致；
- 相同连续文字应合理合并，不能因为固定采样频率产生大量完全重复条目；
- Shot Anchors 只可以辅助采样 / 去冗余，不得把 OCR 输入范围限制为 Reference Clip。

## 6.5 revision / 项目级 Artifact 完整性

单 Episode 完成后，面板显示：

```text
Episode revision
项目 Artifact revision
Raw ASR / OCR count
Canonical dialogue count
OCR span count
```

单集项目中，P6 成功后项目级 `SOURCE_DIALOGUE` 应发布并获得 Artifact revision。

多集项目中必须额外验收完整性门禁：

```text
第 1 集 P6 CURRENT
+
第 2 集尚未完成
↓
第 1 集仍可显示 CURRENT
但项目级 SOURCE_DIALOGUE 尚未发布
artifact_revision = null
```

只有当前 `SOURCE_VIDEO` 中所有 Episode 都有 CURRENT Evidence 后，才允许发布项目级 `SOURCE_DIALOGUE`，其 `episode_sets` 必须覆盖全集。

## 6.6 Source Video 变化后的 STALE

建议使用可丢弃的验收项目进行这一项，避免污染长期项目。

先得到 CURRENT Evidence，然后改变 Source Video，例如：

```text
继续上传 Episode
或
调整 Episode 顺序
```

刷新项目页后预期：

- 新 `SOURCE_VIDEO` revision 成为 CURRENT；
- 旧项目级 `SOURCE_DIALOGUE` 进入 STALE；
- Episode 旧 Evidence 显示 `STALE`；
- 旧 Evidence 仍可读取供人工追溯，但不能继续作为 CURRENT 下游输入；
- 重新运行后形成新的 Evidence revision。

## 6.7 P6 通过标准

只有以下全部满足，才允许把 P6 标记完成：

- 当前代码 / CI 通过；
- 用户从项目页的 P6 开发验收面板亲自显式启动真实任务；
- 使用用户真实短剧运行真实 `faster-whisper`；
- 人工核对 canonical 对白正文与时间戳；
- 人工核对真实 OCR 时间证据；
- 找到真实跨 Shot 对白并确认一条 canonical → 1:N Shot projection；
- 验证无 Shot Anchors 也不会阻塞 P6；
- 验证多 Episode 项目级 Artifact 完整性门禁；
- 验证 Source Video 变化后旧 Evidence / Artifact STALE；
- 确认 canonical Source Evidence 与后续语义模型输出分开存储。

2026-09-09 项目使用者明确确认 P6 人工验收通过，当前正式状态：

```text
P6 = ✅ 完成
SOURCE_DIALOGUE_EVIDENCE = AVAILABLE
P7 = 未开始
```

普通用户最终看到的仍应是“原片理解正在分析 / 证据已准备”，不是 ASR 模型名、OCR 参数或 ProviderJob。

---

# 7. P7 整集多模态理解人工验收要求

P7 进入真实模型后，必须使用完整真实 Episode 做验收。

输入至少包括：

```text
完整 Episode
+
Source Evidence
+
可选 Shot Anchors 时间索引
```

结果至少检查：

- 整集故事梗概是否正确；
- 人物与人物关系是否正确；
- 场景与关键道具是否正确；
- 关键事件 / Story Beats 是否覆盖；
- 时间化剧情是否与原片一致；
- 模型没有因为自己的摘要 / 安全过滤反写覆盖 canonical Source Dialogue；
- 不把重叠的语义时间窗口误当成精确 Shot Boundary。

Step 3.7 Flash 或其他候选必须经过真实 API / Runtime、完整 Episode、结构化输出、延迟 / 成本等独立验收后才能成为生产默认。

---

# 8. P8 逐镜精细拉片人工验收要求

P8 必须在 P7 整集知识已经建立后执行。

禁止验收路径：

```text
每个 Shot 单独丢给模型猜剧情
→ 最后拼成整集
```

正确路径：

```text
Source Bible / Story / Rhythm
+
Shot Anchors / Reference Clip
↓
逐镜精细拉片
```

人工重点检查镜头中的人物、动作、表情、场景、道具、景别、构图、运镜、连续性和剧情功能是否利用了整集上下文，而不是局部盲猜。

---

# 9. 后续统一要求

后续所有阶段继续按本规范执行：

- 工程能力可以逐切片验收；
- 普通产品界面按业务阶段组织；
- GET 无副作用；
- 真实 Provider 必须真实验收；
- 自动测试不能冒充用户真实素材质量；
- 内部 Artifact / Evidence 必须可追溯；
- 不把技术成功冒充业务完成。
