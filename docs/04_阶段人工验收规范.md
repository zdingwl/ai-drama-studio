# 1. 阶段完成的统一标准

每个阶段统一区分：

```text
1. 代码完成
2. 自动测试完成
3. 人工可验收
4. 涉及真实 Provider 时：真实模型 / 真实素材验收
5. 用户明确确认最终 PASS 后才允许升级 Capability availability
```

工程验收入口不等于最终普通用户主流程。

普通用户按业务结果工作；P5/P6/P7/P8/P9/P10 都属于“原片理解”业务阶段内部工程切片。

GET / 页面刷新必须只读；重任务或正式发布只能显式 POST / Command 启动。

“工程实现 + CI 全绿”不能替代真实人工验收，也不能提前把 `PLANNED` 改为 `AVAILABLE`。

## 9.1 真实人工验收必须覆盖

真实验收使用当前已验收短剧 Source 链，不创建虚构 Source Truth。至少检查：

- 初始 GET 与页面刷新不创建 Snapshot/Task/ProviderJob；
- 显式点击“原片分析定稿”后生成 CURRENT `SOURCE_VIDEO_SNAPSHOT`；
- 冻结输入恰好是 11 类 CURRENT Source Artifact；
- Snapshot 中 P5 28 Shot 的 id/number/start/end/duration 与 CURRENT P5 完全一致；
- Snapshot 中 P6 54 条 canonical dialogue 的 id/number/start/end/text/language 与 CURRENT P6 完全一致；
- Snapshot 中 OCR 数量与文本/时间必须与 CURRENT P6 canonical OCR 完全一致，不使用预设数量；
- P7 SOURCE_BIBLE、P8 SOURCE_SHOT_FACTS、P9 Character/Speaker/Scene/Prop 都来自当前正式 revision；
- Character=3、Speaker=3、Scene=3、Prop=4，Speaker 仍独立；
- provenance 的 `provider_jobs=[]`，P10 不产生 ProviderJob；
- 同一 Source chain 再次显式定稿不产生新 revision；
- 使用不会改变语义真相的 P9 Speaker `CONFIRM` 生成一个新 Speaker revision 后，旧 Snapshot 必须变成 STALE；
- 此 STALE 测试不得用错误 MERGE/SPLIT 破坏真实 Source Truth；
- 再次显式定稿应生成新的 CURRENT Snapshot，旧 Snapshot revision 永久保留为 STALE；
- Source Snapshot 不允许 Target/Production 数据回流。
