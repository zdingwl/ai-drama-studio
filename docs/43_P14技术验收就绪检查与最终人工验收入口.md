# P14 技术验收就绪检查与最终人工验收入口

> 日期：2026-09-12  
> 状态：P14 工程验收收口合同；本文补充 `docs/32`、`docs/42`。  
> 本文**不改变阶段状态**：`TTS = PLANNED / TIMING = PLANNED / P14 PASS = NO`。

## 1. 目标

P14 已具备真实 IndexTTS、真实 WAV、逐句 Retake 与确定性 Timing，但“代码能跑”不能等同于“阶段已通过”。

最终人工验收前需要一个只读、可重复执行的技术检查，把以下事实重新核对一次：

```text
CURRENT TARGET_AUDIO
CURRENT TIMING_PLAN
ProviderJob
真实媒体 bytes
SHA256
ffprobe actual_speech_duration_us
Timing 精确重算
```

该检查只回答：

```text
当前正式技术链是否自洽，是否具备进入最终人工听审/确认的条件
```

绝不回答：

```text
声音好不好听
人物表演是否满意
P14 是否 PASS
TTS/TIMING 是否应自动 AVAILABLE
```

## 2. 版本与 Retake lineage 收口

Retake 基线继续允许：

```text
NEEDS_REVIEW candidate
CURRENT TARGET_AUDIO 对应的 ACCEPTED candidate
```

从本文起进一步明确：

```text
历史 ACCEPTED candidate
!=
当前正式 TARGET_AUDIO
```

因此旧正式 revision 的 candidate 即使数据库 review_status 仍是 `ACCEPTED`，只要它已经被新的 TARGET_AUDIO supersede，就不得再作为 Retake 基线。

否则用户可能从旧声音版本重新发起 Retake，形成隐式回滚。

服务端必须通过 CURRENT TARGET_AUDIO typed revision 的 `candidate_id` 验证 ACCEPTED retake base。

## 3. Pending Timing 生命周期

任何 `NEEDS_REVIEW TIMING candidate` 都绑定生成当时的 CURRENT TARGET_AUDIO。

一旦新的 TARGET_AUDIO 被人工 ACCEPT：

```text
old TARGET_AUDIO -> STALE
old TIMING_PLAN  -> STALE
pending timing candidates based on old audio -> SUPERSEDED
```

因此旧 timing candidate 不再允许继续显示为当前可审核 overflow，也不能被用户误认为新音频的 Timing 结果。

新的 TARGET_AUDIO 必须重新执行 Timing 计算。

## 4. duration_factor 产品边界

IndexTTS native adapter 的底层能力可以接受更宽的 duration factor，但 P14 产品合同继续固定：

```text
0.8 <= duration_factor <= 1.25
```

因此：

- typed user command 已在 `0.8~1.25` 校验；
- P14 delivery runtime 也必须再次执行同样校验；
- native adapter 保留更宽底层范围只属于 runtime implementation detail；
- 禁止通过内部调用绕开产品合同，用极端倍速解决 Timing overflow。

## 5. 技术验收检查 API

新增只读接口：

```text
GET /api/v3/projects/{project_id}/p14/acceptance-readiness
```

该 GET：

- 不创建 Task；
- 不创建 ProviderJob；
- 不创建 Candidate；
- 不创建或修改 Artifact；
- 不修改 capability availability；
- 不记录 P14 PASS。

检查当前正式链：

```text
CURRENT TARGET_SCRIPT
-> CURRENT TARGET_AUDIO typed revision
-> clip coverage
-> ProviderJob SUCCEEDED + provider/model lineage
-> candidate task storage 中真实媒体存在
-> media SHA256 与正式 clip 一致
-> 对每条媒体重新 ffprobe
-> ffprobe duration == actual_speech_duration_us
-> CURRENT TIMING_PLAN typed revision
-> target_script / target_audio lineage 一致
-> has_overflow == false
-> 使用当前真实音频重新 compose Timing
-> 重算结果与正式 TIMING_PLAN 完全一致
```

## 6. technical_ready

只有上述自动可证明条件全部满足，返回：

```text
technical_ready = true
blockers = []
```

否则：

```text
technical_ready = false
blockers = [...]
```

`technical_ready=true` 的含义仅为：

```text
可以进入最终人工验收
```

不等于：

```text
P14 PASS
```

## 7. 必须保留的人工检查

自动检查无法判断成片质量，产品面板固定提醒至少完成：

1. 逐句试听：对白清晰完整，无明显截断、吞字、爆音或异常静音；
2. 同一人物声线稳定；
3. 实际听到的内容与 Final Target Dialogue 一致；
4. Acting Direction 没有被念出来；
5. Retake 后的语气、情绪和时长符合剧情意图；
6. Timing 全部 FIT，余量可接受；
7. 没有通过静默改词、极端变速或拉伸镜头解决 overflow；
8. 最后由用户明确确认 `P14 PASS`。

只有第 8 项发生后，才允许另行建立 P14 最终验收记录，并评估把：

```text
TTS
TIMING
```

升级为 `AVAILABLE`。

## 8. UI

产品工作区新增：

```text
P14 · 验收准备
技术验收就绪检查
[运行技术验收检查]
```

检查必须由用户显式触发，因为它会重新读取每条正式 WAV、计算 SHA 并执行 ffprobe；普通页面加载不自动做全量媒体扫描。

UI 显示：

```text
TARGET_AUDIO revision
TIMING_PLAN revision
正式对白数量
ProviderJob 成功数量
媒体 SHA 通过数量
ffprobe 时长一致数量
Timing 覆盖数量
blockers
人工检查清单
```

不得提供“自动 P14 PASS”按钮。
