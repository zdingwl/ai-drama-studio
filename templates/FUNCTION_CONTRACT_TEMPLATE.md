# Function Contract — 简化模板

> 只给“真正影响业务、数据库、文件、状态或外部接口”的核心函数使用。
>
> 简单 helper 不需要写完整 Contract，避免过度设计。

## 什么时候需要完整 Function Contract

满足任一条件时建议填写：

- 核心业务用例，例如 `create_project()`；
- Controller / API 边界；
- 会修改数据库；
- 会写/删文件；
- 会改变核心业务状态；
- 涉及恢复、回滚、安全边界；
- 出错可能影响用户数据。

以下通常不需要完整 Contract：

```text
字符串 trim
日期格式化
表单 reset
简单 Path 拼接
JSON dumps
简单 Router back
纯展示 helper
```

这些只需要：名字清楚 + 必要中文注释 + 有风险时写测试。

# 核心函数必须回答 7 个问题

## 1. 它到底干嘛？

用普通人能看懂的话说明这个函数解决什么问题。

例如不要写：

> “处理项目创建逻辑。”

应该写：

> “把用户填写的新建项目表单真正保存成一个可重新打开的本地项目。”

## 2. 谁调用它？

写清上层入口。

例如：

```text
create_project_api()
→ create_project()
```

## 3. 它会调用谁？

只列重要下层依赖，不需要把每个小 helper 都写进去。

## 4. 输入和输出是什么？

写清核心参数、返回值和业务含义。

## 5. 它会修改什么？

明确：

```text
数据库：读 / 写 / 无
文件：读 / 写 / 删除 / 无
前端状态：修改什么 / 无
网络：有 / 无
```

## 6. 它绝对不能做什么？

这是最重要的一项。

例如 Controller：

```text
不直接 SQL
不 mkdir
不写 project.json
不复制 Service 业务逻辑
```

例如项目清理函数：

```text
绝不能删除用户选择的 Workspace Root
绝不能删除其它 Project
```

## 7. 怎么证明它是对的？

列出最重要的正常、边界和错误测试。

# 中文代码注释最低要求

核心业务函数正式实现时必须有简体中文 docstring。

推荐格式：

```python
def example(...):
    """
    业务作用：
    这个函数替用户/系统完成什么真实动作。

    为什么这样做：
    说明关键设计原因，不机械翻译函数名。

    安全边界：
    明确不能修改/删除/覆盖什么。

    主要异常：
    说明重要失败场景。
    """
```

原则：

> 重要函数讲透；简单函数写清楚；不要为了“单函数开发”制造几十层抽象和几十份文档。
